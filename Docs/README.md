# Гильотинный раскрой Nanxing

Дата фиксации: 2026-06-24

## Цель проекта

Разработать локальную веб-программу для гильотинного раскроя листовых материалов под мебельное производство.

Программа должна заменить/дополнить текущую цепочку расчёта раскроя, устранить ошибки с метражом кромки и ошибками кромки при повороте деталей, а в будущем — уметь формировать файлы для производственной цепочки Nanxing/БАЗИС-подобного формата.

## Первая рабочая версия

Первая версия должна быть простой, локальной и проверяемой:

- Python + FastAPI.
- Доступ по локальной сети.
- Без авторизации.
- Без базы заказов.
- Без учёта материалов.
- Без OCR на первом этапе.
- Без прямой выгрузки в станок на первом этапе.
- Ввод деталей вручную.
- Импорт деталей из Excel.
- Задание разных размеров листов.
- Приоритет использования остатков перед стандартными листами.
- Ширина пилы.
- Отступы от краёв листа.
- Гильотинные резы.
- Пропил считается по фактическому резу, а не прибавляется к каждой детали.
- Визуализация карт раскроя.
- Номер детали, размер и кромка по сторонам на визуализации.
- Точный расчёт кромки с учётом толщины кромки, прифуговки и свеса кромки.
- Excel-отчёт.

## Главный архитектурный принцип

Ядро раскроя не должно зависеть от интерфейса, Excel, OCR, бирок и станочного экспорта.

Поток данных:

```text
Ввод данных
	↓
Проверка и нормализация
	↓
Расчёт размеров и кромки
	↓
Гильотинный раскрой
	↓
Единая внутренняя модель результата
	↓
Экспорты и визуализация
```

Excel, ручной ввод, OCR и будущие импорты должны приводить данные к одной внутренней модели деталей.

## Ручной ввод деталей

Прежний формат из пяти полей поддерживается без изменений:

```text
номер; название; L; W; количество
```

Для ввода кромки используется расширенный формат из девяти полей:

```text
номер; название; L; W; количество; L1; L2; W1; W2
```

Каждая ячейка стороны имеет формат:

```text
толщина|прифуговка|свес|материал
```

После толщины параметры можно не указывать: прифуговка и свес по умолчанию
равны нулю, название материала необязательно. Пустая ячейка, `-` или `—`
означает отсутствие кромки. Десятичные значения принимаются с точкой или
запятой.

Пример:

```text
A1; Фасад; 720; 500; 2; 1|0,5|0|ABS белая; 1; -; -
```

В ручной форме отдельно задаются минимальная длинная сторона, короткая сторона
и площадь возвратного остатка. По умолчанию используются 400×80 мм и 0,04 м².
Результат показывает каждый физически отделяемый прямоугольник, их общую
площадь и отдельный КИМ с учётом возвратных остатков.

Там же выбирается профиль желаемого остатка:

- максимальная полезная площадь — сохраняется максимум суммарной площади;
- длинный остаток — приоритет получает прямоугольник с наибольшей длинной
  стороной;
- компактный остаток — приоритет получает прямоугольник с наибольшим
  вписываемым квадратом.

Профиль по умолчанию — максимальная полезная площадь. Он влияет на выбор только
после размещения всех деталей и минимизации количества и площади нового
материала. Производственные операции сравниваются после ценности остатка.

После одиночной перестройки окон оптимизатор может объединить несколько
непересекающихся уже проверенных окон. Геометрия и дерево резов каждого окна
не пересчитываются, а физические номера деталей сверяются перед объединением.
На обычном заказе этот слой добавляет не более четырёх новых победителей
фиксированных целей; варианты без реального улучшения отбрасываются.

Предельная вместимость проверяется отдельным сервисом
`guillotine_sheet_limit_search.py`. Он принимает явный лимит листов и бюджет
beam-поиска и не запускается из веб-формы автоматически. Отрицательный статус
`not_found_within_budget` означает только, что решение не найдено в заданном
бюджете. Строгая невозможность заявляется лишь при статусе
`proven_impossible_by_area`, когда не сходится нижняя граница по площади.
